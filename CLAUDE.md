# 7600 XT Vulkan SDK - working notes

Read this before changing anything here. It records why each script does what
it does, which is mostly a list of failures that were silent or misleading.

Sibling to `D:\My apps\ROCm SDK`, same machine, same card, same shape: a
recipe, not a toolchain. The scripts fetch LunarG's SDK from the vendor and
put it somewhere `.gitignore`d. **No vendor binary is ever committed.** What is
version controlled is: which package, which version, which components, which
environment variables, and why.

The target is one card: **RX 7600 XT**, `deviceID 0x7480`, AMD proprietary
driver **26.8.1 (LLPC)**, `apiVersion 1.4.349`, conformance 1.4.3.3. Nothing
here has been tried on another.

## The order things run in

```powershell
scripts\get_vulkan_sdk.ps1 -Installer <the LunarG SDK installer>
scripts\verify.ps1                        # do not skip this
scripts\smoke_test.ps1
```

`vkenv.ps1` is dot-sourced by the other three and can be dot-sourced by hand to
get a shell with the SDK and MSVC on it.

`main` builds nothing. Anything built on top belongs on a branch, as in the
ROCm repository:

| branch | what it builds | measured |
| --- | --- | --- |
| `cooperative-matrix` | the matrix units through `VK_KHR_cooperative_matrix`, and a GEMM on top of them | 46,471 GFLOP/s for the instruction, 3.4x the fp32 vector ceiling; 19,206 GFLOP/s for a 2x2 blocked GEMM, 41% of it |

# Part 1 - what the SDK is

## It is not the loader

The SDK is headers, import libraries, layers and tools. `vulkan-1.dll` in
System32 comes from the graphics driver, or from LunarG's separate
`VulkanRT-...-Installer.exe`, and *that* one wants elevation for a reason - it
writes to System32. The SDK does not contain it.

Consequence worth knowing before it wastes an afternoon: **`vulkaninfo.exe` on
PATH is the runtime's, in System32, not the SDK's.** The SDK ships its copy as
`vulkaninfoSDK.exe` precisely so the two do not collide. Every script here
calls `vulkaninfoSDK.exe` by full path, because a check that silently asked a
different loader about a different layer set is worse than no check.

`Helpers\VulkanRT.exe` inside the SDK tree is that runtime installer, bundled.
`Helpers\` also holds `install_helper.exe` and `launch_helper.exe`, which are
the installer's own machinery, not yours.

## What is actually in the tree

Core alone is **1.70 GB**, and 1.6 GB of that is two directories:

| directory | size | what |
| --- | --- | --- |
| `Bin` | 817 MB | 82 entries: every tool and every layer DLL |
| `Lib` | 782 MB | import libraries, static libraries, and `Lib\cmake` |
| `Include` | 36 MB | `vulkan`, `vk_video`, plus glslang, shaderc, slang, dxc, spirv, spirv_cross, spirv-tools headers |
| `Helpers` | 28 MB | the bundled VulkanRT installer and installer machinery |
| `share` | 20 MB | `share\vulkan\registry`: `vk.xml`, `video.xml`, `validusage.json`, the profiles schema and its two generator scripts |
| `Config` | 908 KB | `vk_layer_settings.txt`, generated by Vulkan Configurator 3.5.1 |
| `Source` | 676 KB | SPIRV-Reflect, shipped as source because you are meant to vendor it |
| `Templates` | 85 KB | a Visual Studio 2022 project template |

`maintenancetool.exe` at the root is another 34 MB and is not decoration - it
is the only working way to change the component set after the fact. See below.

## Four shader compilers, and which one you want

They are all in `Bin` and they are not interchangeable:

| tool | version here | takes | notes |
| --- | --- | --- | --- |
| `glslc` | shaderc v2026.3 | GLSL, HLSL | gcc-style flags, `-O`, `-fshader-stage`. The default choice; `smoke_test.ps1` uses it |
| `glslangValidator` | glslang 16.4.0 | GLSL, HLSL | the reference front end, Khronos flag style. `glslang.exe` is the same binary under its newer name |
| `slangc` | slang 2026.13.1 | Slang | a different language that targets SPIR-V; modules, generics, autodiff |
| `dxc` | 1.9.0.5399 | HLSL | Microsoft's, with the SPIR-V backend enabled |

And after any of them, `spirv-val` decides whether the result is legal.
**glslc emitting a module glslc is happy with is not the same as one a driver
will accept**, which is why `smoke_test.ps1` runs the validator as a separate
step with its own failure message rather than trusting the compiler's exit
code.

The rest of the `spirv-*` set is worth knowing exists: `spirv-dis`/`spirv-as`
to read and write the text form, `spirv-opt` for optimisation passes,
`spirv-cross` to go *back* to GLSL/HLSL/MSL, `spirv-reflect` for the interface,
`spirv-link`, `spirv-diff`, `spirv-lint`, `spirv-reduce` for shrinking a
module that reproduces a bug.

`gfxrecon-*` capture and replay whole applications; `vkconfig` and
`vkconfig-gui` write the layer settings that `Config\vk_layer_settings.txt` is
an example of; `vkcube` and `vkcubepp` are the "does anything work at all"
triangle; `vulkanCapsViewer` is the GUI version of vulkaninfo.

## `Lib\cmake` is not the Vulkan package

CMake's own `find_package(Vulkan)` finds the SDK through the `VULKAN_SDK`
environment variable and needs nothing from `Lib\cmake`. What is in there is
config packages for the *tools* - `glslang`, the eight `SPIRV-Tools-*`
packages, and nine `spirv_cross_*` - for when you link the compiler stack into
your own program rather than shelling out to it.

# Part 2 - getting it installed cold

Proved on 2026-08-25 by installing a second, independent copy to
`D:\vk-cold\1.4.357.0` on a machine that already had one on C:, then removing
it again. The full transcript is `samples/cold-install.txt`. Three things cost
a run each.

## The installer has a real command line

It is a Qt Installer Framework package. `installer.exe --help` documents the
lot, `installer.exe search` prints the packages, and neither needs the wizard.

```
installer.exe --root <dir> --accept-licenses --default-answer --confirm-command install <packages>
```

The package names are not guessable and are not in the SDK documentation this
project found. They come out of `search`, which prints an `<availablepackages>`
XML block. As of **1.4.357.0**:

| package | what |
| --- | --- |
| `com.lunarg.vulkan` | the root |
| `com.lunarg.vulkan.core` | everything below, marked "Always Installed" |
| `com.lunarg.vulkan.debug` | shader toolchain debug symbols, 64-bit |
| `com.lunarg.vulkan.sdl2` | SDL libraries and headers |
| `com.lunarg.vulkan.glm` | GLM headers |
| `com.lunarg.vulkan.vma` | Vulkan Memory Allocator header |
| `com.lunarg.vulkan.volk` | volk header, source and library |
| `com.lunarg.vulkan.arm64` | ARM64 binaries for cross compiling |

Run `search` again when the version moves rather than trusting that table. The
installer contacts LunarG's repositories to do it, so `search` and `install`
both want a network.

## Failure 1: two flags that cannot both be passed

```
The following options are mutually exclusive: accept-messages, default-answer.
```

Printed as the **last line after a screen and a half of `--help`**, with exit
code 1 and nothing before it that reads like an error. Both flags look like
things a headless install wants. `--default-answer` is the one to keep: it
answers each query with the answer the vendor marked as the default, rather
than accepting every one of them.

## Failure 2: it cannot be run unelevated

Without elevation the installer extracts every archive, gets as far as
`Installing component The Vulkan SDK Core`, and then:

```
installationError : Error : Cannot elevate access rights while running from
command line. Please restart the application as administrator.
Answer: "NoButton"
ROLLING BACK operations= 26
Installation aborted!
```

45 seconds of apparent progress and then a clean rollback. The elevated work
is real - registering the layer manifests under HKLM and running the bundled
VC_redist - so there is no flag that skips it, and `--auto-answer` cannot get
past it either:

```
Invalid answer "Ignore" for "installationError". Using default value "NoButton" instead.
```

The query offers no buttons, so no answer continues.

`get_vulkan_sdk.ps1` therefore checks for elevation **before writing
anything** and relaunches itself through UAC. Three details of that relaunch
are each their own failed attempt:

- **A shell is elevated, not the installer.** `-Verb` and
  `-RedirectStandardOutput` are in different `Start-Process` parameter sets;
  asking for both is not a runtime error but `Parameter set cannot be
  resolved` before anything runs. The redirect is worth keeping, because an
  elevated process gets its own console that closes when it exits, and on
  failure the installer rolls back and deletes the `InstallationLog.txt` it
  would otherwise have left in the destination.
- **The work goes in a generated script file, not `-Command`.** A `-Command`
  string handed through `-ArgumentList` loses its inner quoting somewhere in
  the round trip, and the failure shape is the nastiest kind: the child still
  exits with the code the string ends in, so **it reports success having
  silently done nothing**. That cost two runs before the probe that caught it.
- **Windows PowerShell at its System32 path**, not `$PSHOME` and not whatever
  is running the script. On this machine `pwsh` is the Store build out of
  `C:\Program Files\WindowsApps`, and an elevated Store-packaged shell runs,
  exits with the right code, and lands **none** of its file writes.

## Failure 3: the component list is not a component list

Naming packages after `install` does not restrict the install to them. It adds
them to LunarG's default selection. With `com.lunarg.vulkan
com.lunarg.vulkan.core` on the command line **and
`--no-default-installations` as well**, the log says:

```
Selected components without dependencies:
com.lunarg.vulkan  com.lunarg.vulkan.core  com.lunarg.vulkan.glm
com.lunarg.vulkan.sdl2  com.lunarg.vulkan.volk  com.lunarg.vulkan.debug
com.lunarg.vulkan.vma  com.lunarg.vulkan.arm64
Installation space required: "4.99 GB"
```

Two of eight asked for. `--no-default-installations` is the documented flag
for exactly this and does not do it here.

What works is the maintenance tool the install has just left behind:

```
maintenancetool.exe rm com.lunarg.vulkan.glm com.lunarg.vulkan.sdl2 ... --default-answer --confirm-command
```

**4.97 GB becomes 1.70 GB**, `components.xml` drops to the two entries that
were asked for, it takes under a second because it only deletes, and unlike
the install it **needs no elevation**. 1.70 GB is also byte for byte what the
wizard produces for core alone, so the two routes converge.

`get_vulkan_sdk.ps1` runs that removal automatically for any optional package
the caller did not name, which is the only reason its `-Components` parameter
means anything.

## What the install did to the machine

This is the part to watch, and it is not in any LunarG documentation found
here.

Before the cold install, `HKLM\SOFTWARE\Khronos\Vulkan\ExplicitLayers` held
nine manifests under `C:\VulkanSDK\1.4.357.0\Bin`. Afterwards it held nine
under `D:\vk-cold\1.4.357.0\Bin` and **none** under C:.

The second SDK did not add itself alongside the first. It repointed every
explicit layer entry at itself, and the first SDK's layers stopped being
discoverable - silently, with both trees still on disk and both looking
complete. Anyone with two SDK versions installed is running the layers of
whichever was installed last, whatever `VULKAN_SDK` says.

`maintenancetool.exe purge` then removed the tree and left nine registry
entries pointing at files that no longer existed. It did not restore C:'s.
Those were put back by hand.

# Part 3 - layers, which is where Vulkan hides its state

## Discovery, in the order the loader does it

Explicit layers - the ones an application must ask for by name - come from
`HKLM\SOFTWARE\Khronos\Vulkan\ExplicitLayers` and the `HKCU` equivalent, plus
any directory in `VK_LAYER_PATH` or `VK_ADD_LAYER_PATH`. Implicit layers - the
ones that load themselves into every process without being asked - come from
`...\ImplicitLayers` under both hives. Each registry *value name* is the full
path to a `.json` manifest and the data is a DWORD 0.

## `VK_ADD_LAYER_PATH`, never `VK_LAYER_PATH`

The two look interchangeable and are not. **`VK_LAYER_PATH` replaces
discovery**, so setting it hides every layer the driver and the overlays
registered, and an overlay problem then cannot be reproduced from that shell.
`VK_ADD_LAYER_PATH` prepends and keeps the rest.

And `vkenv.ps1` sets even that **only when the validation layer is not already
enumerable**. The first draft set it unconditionally, which looked harmless
and was not: the installer already registers the SDK's manifests, so pointing
a search path at the same directory made the loader emit eight

```
Removing layer VK_LAYER_... because it is a duplicate of VK_LAYER_...
```

warnings on every single run, each naming the same file twice. Eight lines of
noise on top of a program whose whole job is to make the messages that matter
visible. Deleting that one assignment removed all eight.

## Ten layers on this machine belong to somebody else

`verify.ps1` ends with a note rather than a check:

```
GalaxyOverlayVkLayer / _DEBUG / _VERBOSE     GOG Galaxy
VK_LAYER_AMD_switchable_graphics             driver, registered twice
VK_LAYER_EOS_Overlay                         Epic Online Services
VK_LAYER_OBS_HOOK, VK_LAYER_WEOBS_HOOK       OBS, and a second OBS hook under
                                             C:\ProgramData\lovense-obs-studio-hook
VK_LAYER_ROCKSTAR_GAMES_social_club
VK_LAYER_VALVE_steam_fossilize               Steam pipeline cache
VK_LAYER_VALVE_steam_overlay
```

Every one is a DLL loaded into a Vulkan process before the driver answers.
Three are registered twice over and the loader says so on every run. Before
believing a capture, a hang, or a frame time from this machine:

```powershell
$env:VK_LOADER_LAYERS_DISABLE = "*"
```

That is this repository's equivalent of the idle guard in the ROCm
repository's `card_report.ps1`: the instrument has to be quiet before the
reading means anything. `VK_LOADER_LAYERS_ENABLE` is the same syntax in
reverse, and both take globs, so `VK_LOADER_LAYERS_DISABLE=~implicit~` turns
off the self-loading ones and keeps the rest.

## Configuring a layer without a GUI

`Config\vk_layer_settings.txt` is a worked example generated by Vulkan
Configurator, with every setting of every LunarG layer written out and
commented. Copy it next to the executable, or point `VK_LAYER_SETTINGS_PATH`
at it. `vkconfig.exe` is the command line version of the same thing. This is
how you turn on the validation layer's expensive checks - GPU-assisted
validation, best-practices, synchronisation - none of which are on by default.

# Part 4 - the card, as the SDK reports it

Reported capability, not measurement. Nothing below was timed.

**Queue families**, which decide what `smoke_test.cpp` can pick:

| family | count | flags |
| --- | --- | --- |
| 0 | 8 | graphics, compute, transfer, sparse binding |
| 1 | 8 | compute, transfer, sparse binding |
| 2 | 1 | transfer, sparse binding |
| 3 | 1 | video encode |
| 4 | 1 | video decode |

The smoke test takes the first family with `VK_QUEUE_COMPUTE_BIT`, which is
family 0. Family 1 is the async compute path and is what a real workload
should use to overlap with graphics.

**Memory**: three heaps, sixteen types.

| heap | size | flags |
| --- | --- | --- |
| 0 | 15.73 GiB | device local |
| 1 | 15.57 GiB | host, no flags |
| 2 | **256 MiB** | device local **and** host visible and coherent |

Heap 2 is the BAR window, and 256 MiB of it means resizable BAR is not in play
here. It is the fast path for small host writes the GPU reads directly, and it
is small enough to run out of without noticing. The smoke test does not use
it: it asks for `HOST_VISIBLE | HOST_COHERENT` and takes the first matching
type, which lands in heap 1.

Two of heap 2's types also carry `DEVICE_COHERENT_BIT_AMD` and
`DEVICE_UNCACHED_BIT_AMD` - AMD's uncached path, for when the CPU must see
device writes without a fence.

**220 device extensions**, and two entries in that list matter for anything
this repository might do next:

- `subgroupSize = 64`, `minSubgroupSize 32`, `maxSubgroupSize 64`, with
  `subgroupSizeControl = true`. RDNA 3's wave32/wave64 choice, exposed and
  settable per pipeline.
- **`VK_KHR_cooperative_matrix`, revision 2, `cooperativeMatrix = true`**,
  supported in `SHADER_STAGE_COMPUTE_BIT` only, `shaderBFloat16CooperativeMatrix
  = false`.

That last one is the direct counterpart of the ROCm repository's WMMA work,
which measured the matrix units at 39.1 TFLOP/s, 4.1x the fp32 vector ceiling,
and separately found that token generation dispatches 6,211 kernels **without
using a single matrix instruction**. The Vulkan path to those same units
exists on this card and has not been touched here.

# Part 5 - the scripts themselves

## Why the smoke test is longer than the HIP one

Three things can break and only one of them is the compiler, so the script
keeps them apart: `glslc` turning GLSL into SPIR-V, `spirv-val` agreeing the
SPIR-V is well formed, and the driver running it. A failure names which.

And the host program switches the **validation layer on and fails the run if
it objects**, exit code 5, separate from "wrong answer", exit code 4. This is
the part with no HIP equivalent and the reason the file is 350 lines: a Vulkan
program containing a genuine misuse usually still runs and still prints the
right numbers. The only way that failure becomes visible is to decide, up
front, that a complaint from the layer ends the run.

The teardown destroys every object in order for the same reason - the layer
reports the ones that are not destroyed, so a leak would mean the
clean-validation claim was made about an incomplete run. The output buffer is
filled with `-1.0f` before the dispatch, so "the shader did nothing" and "the
shader wrote zeroes" are different failures. The messenger is chained into
`VkInstanceCreateInfo.pNext` as well as created as an object, because misuse
*during instance creation* happens before the object can exist.

## Choosing the device

This machine enumerates **two** Radeons - the discrete 7600 XT and the
integrated part in the processor. Today the discrete one is index 0, and
nothing guarantees that: "device 0" is the integrated GPU on plenty of
machines. `smoke_test.cpp` takes a device name substring, matches on
`deviceName`, and prints the name it actually used. A benchmark that quietly
ran on the integrated GPU would look like a slow card, and would look like a
slow card consistently.

## Small things that are deliberate

- **No space in the SDK path**, checked twice. The SDK's own CMake configs
  take paths from `VULKAN_SDK` unquoted in places; a space fails somewhere
  else, later, in a message that names neither.
- **MSVC comes from `vswhere`**, not a pinned toolset. Vulkan needs no
  particular one, and `vswhere.exe` sits at a fixed path under
  `Program Files (x86)\Microsoft Visual Studio\Installer` for every VS since
  2017 including Build Tools. `vcvars64.bat` is run in a child `cmd` and its
  environment copied back, rather than `INCLUDE` and `LIB` being written by
  hand - those lists move between VS versions.
- **`glslc -O`.** An unoptimised module goes through a different path in the
  driver's compiler than anything real will.
- **A 10-second fence timeout** rather than `UINT64_MAX`. A hung dispatch
  should end the test, not the shell it was run from.
- **`get_vulkan_sdk.ps1` re-checks four files after the install and after the
  removal pass.** The installer exits zero when handed a package name that
  does not exist and has silently skipped it, and the removal pass is a second
  chance to have deleted something needed.
- **`verify.ps1` dot-sources `vkenv.ps1`** rather than assuming an
  environment, so it checks what the build scripts will get rather than
  whatever is left over in the current shell.
- **One PowerShell bug worth remembering.** `$hit = $names | Where-Object {...}`
  returns a bare string when exactly one thing matches, and indexing a string
  gives a character. The device check printed `index -1 of 2` for a device it
  had just found. `@()` around the filter.

## Measured so far

On `main`, nothing, and that is deliberate: it proves the SDK works and has no
opinion about the card. There is still no Vulkan equivalent of
`card_report.ps1` - bandwidth against the processor, and a single report that
covers the card rather than one instruction, are both unwritten.

The instruction ceilings and one GEMM are measured on the `cooperative-matrix`
branch; see the table above and that branch's `projects/cooperative-matrix/NOTES.md`.
Do not let this file imply anything beyond that has been measured.

What is proven, on 2026-08-25:

- `samples/first-run.txt` - SDK 1.4.357.0, `VK_HEADER_VERSION 357`, loader
  1.4.357.0, MSVC 19.51.36252, 1176 bytes of SPIR-V, 1024 elements correct on
  the 7600 XT with the validation layer clean.
- `samples/cold-install.txt` - the same, from an SDK installed from nothing to
  a second location, before and after trimming 4.97 GB to 1.70 GB.

The obvious next branch is the one the extension list points at:
`VK_KHR_cooperative_matrix` in compute, measured against the fp32 vector
ceiling on the same card, and compared with the 39.1 TFLOP/s the ROCm
repository measured through WMMA. Two paths to the same silicon, and no reason
yet to believe they land in the same place.
