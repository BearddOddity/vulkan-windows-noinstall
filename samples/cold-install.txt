# Cold install, 2026-08-25
#
# A machine that already had an SDK at C:\VulkanSDK\1.4.357.0 was used to
# install a second, independent copy to D:\vk-cold\1.4.357.0 from nothing, to
# prove scripts\get_vulkan_sdk.ps1 against a real installer rather than
# against a tree the wizard had already made.
#
# The three failures below happened in this order and each cost a run. The
# script now handles all three; they are kept here because the messages are
# what you would search for.


## 1. The flags that cannot be used together

$ vulkansdk-windows-X64-1.4.357.0.exe --root D:\vk-cold\1.4.357.0
      --accept-licenses --accept-messages --default-answer --confirm-command
      install com.lunarg.vulkan com.lunarg.vulkan.core

  [ ... a screen and a half of --help ... ]
  The following options are mutually exclusive: accept-messages, default-answer.

  exit 1

Printed as the last line after the whole of --help, with nothing that reads
like an error before it. --default-answer is the one to keep.

Every archive extracts first, so it looks like a working install until the

The query offers no buttons, so there is no answer that continues.

## What the script does about it

  installed, 4.97 GB
  removing components that were installed without being asked for:
    com.lunarg.vulkan.debug
    com.lunarg.vulkan.sdl2
    com.lunarg.vulkan.glm
    com.lunarg.vulkan.vma
    com.lunarg.vulkan.volk
    com.lunarg.vulkan.arm64
  [349] Components uninstalled successfully

  4.97 GB -> 1.70 GB, and components.xml now lists com.lunarg.vulkan and
  com.lunarg.vulkan.core alone. That is byte for byte the size of the wizard's
  core-only install on C:.

  The removal took 0.4 seconds and needed no elevation. Only the install does.

## What the install did to the machine, which is the part to watch

Before, HKLM\SOFTWARE\Khronos\Vulkan\ExplicitLayers held nine manifests under
C:\VulkanSDK\1.4.357.0\Bin. After the cold install it held nine under
D:\vk-cold\1.4.357.0\Bin and none under C:.

The second SDK did not add itself alongside the first. It **repointed every
explicit layer entry at itself**, and the first SDK's layers stopped being
discoverable - silently, with both trees still on disk and both looking
complete. vkenv.ps1 survives this only because it checks whether the
validation layer is enumerable before deciding to set VK_ADD_LAYER_PATH.

`maintenancetool.exe purge` removed the tree and left the registry with nine
entries pointing at files that no longer existed; the C: entries were not
restored. They were put back by hand.
